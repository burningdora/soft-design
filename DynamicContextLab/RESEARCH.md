# Лабораторная 4: контекст с динамическими свойствами

Это документ о том, что я изучила и в каком порядке думала при выполнении работы.
Код: решение `DynamicContextLab.sln` (три проекта).

---

## 1. Что такое контекст с динамическими свойствами

**Ситуация.** Есть код, который умеет делать что-то общее: проходить по дереву, гонять шаги pipeline,
обновлять игровые сущности. Он написан заранее и не знает, какие данные понадобятся тем, кто его использует.
Пользователь задаёт операцию (стратегию), и этой операции нужны данные: сумма, имя, коэффициент.

**Проблема.** Операцию вызывает не пользователь, а общий код. Передать данные напрямую некуда.
Варианты «положить данные в поле операции» или «в глобальную переменную» плохи: нельзя безопасно
запустить параллельно из двух потоков, данные смешиваются между запусками.

**Решение.** Общий код принимает объект-контекст снаружи и передаёт его операциям, не заглядывая внутрь.
Пользователь кладёт в контекст свои данные, операции их достают. Библиотека про эти данные ничего не знает.

## 2. Примеры в существующих библиотеках

Названия свойств и типы я записала по памяти и документации, перед сдачей их стоит ещё раз
сверить в официальной документации.

| Библиотека | Контекст | Динамические свойства | Для чего |
|---|---|---|---|
| ASP.NET Core | `HttpContext` | `Items` (`IDictionary<object, object?>`) | middleware передают друг другу данные в пределах одного запроса |
| ASP.NET Core Authentication | `AuthenticationProperties` | `Items` (строки), `Parameters` (объекты) | передать приложению данные через процесс входа |
| ASP.NET Core MVC | `ActionExecutingContext` | `ActionArguments` (в тексте задания названо `ActionParameters`) | фильтр читает и подменяет аргументы действия |
| FluentValidation | `ValidationContext<T>` | `RootContextData` | передать в правила валидации данные, неизвестные библиотеке |
| HotChocolate (GraphQL) | `IResolverContext` | `ContextData` | передача данных между резолверами и middleware |
| .NET | `Exception` | `Data` | прикрепить к ошибке произвольные пары ключ-значение |
| WPF | `DependencyObject` | `DependencyProperty.Register` | свойства, которые регистрируются в глобальном реестре по имени |

**Пример с кодом (ASP.NET Core).** Первый middleware кладёт данные, второй их читает.
Каждый из них написан отдельно, а общий тип `HttpContext` у них один и тот же:

```csharp
app.Use(async (ctx, next) =>
{
    ctx.Items["startedAt"] = DateTime.UtcNow;      // положили
    await next();
});

app.Use(async (ctx, next) =>
{
    var startedAt = (DateTime)ctx.Items["startedAt"]!;   // достали и привели тип
    await next();
});
```

Здесь видны слабые места, которые мы потом исправляем: ключ это просто строка, тип нужно приводить руками,
опечатка в ключе обнаружится только при запуске. WPF в этом смысле лучше: свойство регистрируется в реестре,
а повторная регистрация того же имени для того же типа, насколько я знаю, приводит к исключению.
Это та же идея, что и наш реестр ключей.

## 3. Почему не подходит Fat Struct, если проект это библиотека

**Fat Struct** это один большой тип, в котором лежат поля вообще для всех возможных случаев.
Для приложения целиком это простой и удобный вариант: всё статически типизировано.
Для библиотеки он не работает, потому что:

1. **Библиотека не знает потребителей.** Она собирается раньше и ничего не знает о проектах, которые на неё сошлются.
   Поля вроде `Brightness` или `Camera` ей взять неоткуда.
2. **Потребитель не может править чужой тип.** Структура лежит в уже скомпилированной сборке.
   Добавить в неё поле можно только изменив саму библиотеку.
3. **Зависимость идёт не в ту сторону.** Если вписать в библиотеку поля всех потребителей, то она начнёт зависеть от них.
   Каждый новый потребитель потребует новой версии библиотеки.
4. **Два потребителя ломают друг друга.** У одного поле `Name` строка, у другого число. В одной структуре они не уживутся.
5. **Трата памяти и проверки.** Все поля есть в каждом экземпляре, даже ненужные, и приходится проверять, задано ли поле.

Поэтому библиотека хранит данные динамически: словарь, в который потребитель кладёт свои значения.

## 4. Ход мыслей: какие подходы я рассмотрела

Я шла в том же порядке, что и лекция.

| Шаг | Подход | Что получили | Что плохо |
|---|---|---|---|
| 1 | Данные в полях операции | просто | нельзя менять данные без доступа к операции, нет безопасности потоков |
| 2 | Fat Struct | статические типы | не годится для библиотеки (см. раздел 3) |
| 3 | Абстрактный класс контекста + наследники | потребитель определяет свои данные | каст в конкретный тип, ошибка только при запуске, нельзя смешать операции с разными контекстами |
| 4 | Интерфейсы + generics (`Pipeline<TContext>`, контравариантность `in T`) | статическая типизация и гибкость | всё равно нужно заранее описывать типы контекста |
| 5 | `object[]` с константами-индексами | данные любые | коллизии индексов, массив с лишними ячейками, boxing, касты |
| 6 | `Dictionary<int, object>` | нет лишней памяти, `Add` выбрасывает исключение при повторе ключа | касты, ключ-число ничего не говорит о типе |
| 7 | **Типизированный ключ `Key<T>`** | тип значения известен из ключа, касты не нужны | можно создать ключ вручную и подделать тип |
| 8 | **Реестр ключей** | два проекта не получат один и тот же ключ | порядок регистрации влияет на числа ключей |
| 9 | **`internal` конструктор ключа** | из другого проекта ключ создать нельзя | остаётся только `default(Key<T>)`, его обрабатываем отдельно |

Я остановилась на шагах 6–9: словарь, типизированный ключ, реестр и закрытый конструктор.
Альтернативы, о которых я прочитала, но не делала: список компонентов с поиском по типу (как в Unity),
строковые ключи (проще, но медленнее из-за хеша и больше шансов на конфликт),
ECS (Sparse Set или архетипы) это самый эффективный вариант для игр: отдельный массив на каждый тип данных,
сущность это просто идентификатор.

## 5. Как устроено решение

```
DynamicContext (библиотека)      ExifModule (потребитель 2)      PhotoApp (потребитель 1, exe)
  IKey, Key<T>                     ExifKeys                        PhotoKeys
  KeyRegistry (Singleton)          ExifReportSystem                PrintSystem
  Entity                                                           Program (демонстрация)
  ISystem, World
        ^                                ^                              |
        |________________________________|______________________________|
                    оба проекта ссылаются на библиотеку; библиотека не знает о них
```

* `Key<T>` хранит число и зашитый тип значения. Конструктор `internal`, ключ можно получить только из реестра.
* `KeyRegistry.Global` (Singleton) выдаёт ключи и помнит имя, тип и место регистрации (файл:строка).
  Повторная регистрация имени даёт `KeyAlreadyRegisteredException`. Номера ключей начинаются с 1,
  поэтому `default(Key<T>)` (номер 0) не совпадёт ни с каким настоящим ключом.
* `Entity` хранит `Dictionary<int, object?>`. Методы `Add`, `Set`, `Get`, `TryGet` принимают `Key<T>`,
  поэтому запись значения неверного типа не компилируется, а `Get` возвращает уже нужный тип.
* `World` хранит сущности и операции (`ISystem`). Операция применяется только к сущностям,
  у которых есть все свойства из `Requires`.
* Потребитель задаёт **части сущностей** (ключи и значения) и **операции** (лямбда или класс `ISystem`).

## 7. Ограничения (честно)

* Значения хранятся как `object`, поэтому типы-значения (`int`) упаковываются (boxing). Это решают пулом объектов или ECS.
* Реестр защищён блокировкой, а сам `Entity` не потокобезопасен.
* Числа ключей зависят от порядка регистрации, поэтому их нельзя сохранять на диск, сохранять нужно имена.
* Подделать ключ можно только через рефлексию.
* Поиск по словарю медленнее, чем по полю структуры.
